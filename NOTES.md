1. HOW THE PROJECT WORKS AND WHY THE REGISTERS ARE NEEDED

The project implements a valid/ready data pipeline in the rtl/full_pipeline.sv module

The main idea is to separate the input and output sides with a two-registers buffer storing up two data word:
- s_valid = 1 - the upstream block is offering valid data,
- s_ready = 1 - the module can accept data,
- m_valid = 1 - a valid word is present in the buffer,
- m_ready = 1 - the downstream block can accept data.

A transfer occurs only when the corresponding valid/ready pair is simultaneously equal to 1.
After reset, m_valid is cleared, so the module does not present any data as valid at the output.

The pipeline uses a two data registers, two flags, and a 2-bit counter.

Flags:
- do_write = s_ready && s_valid
- do_read = m_valid && m_ready

The registers are primarily required because the specification prohibits a direct combinational path from input to output. By registering the data:
- input data is sampled on the clock edge,
- it remains stable while waiting for m_ready = 1,
- the output can be stalled for any number of backpressure cycles,
- changes to the input data do not directly affect m_data.

Handshake handling:
s_valid && s_ready - the input transfer is considered complete,
m_valid && m_ready - the output transfer is considered complete.

If m_valid = 1 and m_ready = 0, the data remains in the register and cannot be overwritten. This is essential for correct backpressure handling.

The system consists of a 1x2 demultiplexer, two parallel registers, and a 2x1 multiplexer.

Upon receiving an input handshake, the input data is written to the register selected by the demultiplexer. For the next write operation, the demultiplexer points to the other register. The demultiplexer alternates between the registers.

A counter is used, which increments when a register write occurs and decrements when a read occurs.

When the counter value is less than 2, the s_ready signal is equal to 1.
When the counter value is greater than 0, the m_valid signal is equal to 1.

A 2x1 multiplexer is used for reading. The multiplexer reads the register written in the previous cycle after receiving output handshake, alternating the selection of registers for read operations.

The testbench checks that words leave the module in the same order in which they were accepted at the input.

The implemented send() task sends the data generated by the testbench to the buffer and then waits for the next clock edge to ensure signal stability and satisfy the timing requirements. If s_ready is low, send() waits for the next clock cycle until s_ready becomes high. Immediately after the rising clock edge on which the data is accepted, s_valid and s_data are set to 0 and 'x, respectively.

The implemented scoreboard stores every data word generated by the testbench in the "expected[$]" queue after the input handshake condition is met. Then, after the output handshake condition is met, the following cases are checked:
- whether the queue is empty after m_valid = 1 is observed,
- whether m_data matches the expected data from the "expected" queue.

If the data does not match, an ERROR message about the data mismatch is printed.
If the data matches, a PASS message confirming the data match is printed.


2. IMPORTANT ASSUMPTIONS AND DESIGN DECISIONS

Assumptions:
- the signals are synchronous with the rising edge of clock,
- the reset is synchronous and active-high,
- the reset occurs only at the beginning of the simulation,
- dmux 1x2 on the input is used,
- two parallel registers are used,
- mux 2x1 on the output is used,
- two flags are used, 
- 2-bits counter is used,
- no additional AXI4-Stream signals such as TLAST or TKEEP are used,
- a ready-made FIFO is not used,
- the solution is synthesizable and does not require formal verification,
- there is no assumption that m_ready is always asserted; the module must retain the data when m_ready = 0.


3. make test RESULT AND WHAT IT SAYS ABOUT THE PROJECT

An example output after completing the implementation can be found in the file log_file.txt. 

The actual result depends on the implementation version, number of words, and random parameters.

Before implementing send(), the provided testbench ended with a timeout, which is expected according to the task description.

For every output handshake an information whether m_data == expected[0] is printed.

The scripts/analyze.py script processes the build/sink.txt file.

Script reports every detected phase. If there is data but phase was not detected before, an ERROR message is printed. 

The following are reported for each detected phase:
- number of words accepted at the input,
- number of words received at the output,
- throughput in words/cycle,
- latency of the first word,
- number of cycles associated with backpressure on each side.

5. LIMITATIONS AND POSSIBLE IMPROVEMENTS

The following should be considered:
- using an active-low asynchronous reset,
- more extensive corner-case tests,
- tests with different random seeds,
- test with different m_ready probability,
- adding additional elements in testbench like: monitor, interface,
- implementing a parameterizable FIFO module that would improve buffer performance using read and write pointers.
